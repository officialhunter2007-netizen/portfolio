GitOps on Kubernetes with EKS Fargate and ArgoCD

The pipeline never touches the cluster. It builds an image and commits the new tag to Git; ArgoCD notices and makes the cluster match.

The problem

In Project 6 the pipeline pushed straight to ECS. That works for one service, but every extra service needs its own task definition, ECS service, target group and listener rule, and the pipeline holds the power to change production. I wanted one API for many workloads, and Git, not a CI job, to be the record of what runs.

Architecture

Three systems each own one thing, so changes never mix:

  • Terraform owns AWS: VPC, EKS, three Fargate profiles, ECR, IAM, the load balancer controller policy.
  • GitHub Actions owns the build: authenticate with OIDC, build the image, push it to ECR, commit the new tag.
  • ArgoCD owns the cluster: it reconciles k8s/production against what is running.

How a change reaches the cluster

  1. Push to main in project-7-app.
  2. The workflow assumes an AWS role through GitHub OIDC, builds the image and pushes it to ECR tagged with github.sha.
  3. It checks out project-7-gitops, rewrites the image: line in deployment.yaml and commits as the Actions bot.
  4. ArgoCD sees the new commit and applies it. Kubernetes performs a rolling update.

If the pipeline fails after pushing the image but before committing the tag, the cluster simply keeps running the previous version.

# argocd-app.yaml
syncPolicy:
  automated:
    prune: true      # delete what is no longer in Git
    selfHeal: true   # revert manual drift in the cluster

Engineering decisions

EKS on Fargate instead of managed nodes

Keeps the serverless cost and operations model from Project 6: no nodes to patch or size. Each pod gets its own Fargate instance and VPC IP. Cost: less control over the host, and every namespace that runs pods needs a Fargate profile.

Separate liveness and readiness probes

/live means "restart me if this fails"; /ready means "stop sending me traffic". The app returns 503 from /ready for its first 20 seconds, simulating start-up work, and the pytest suite asserts that behaviour. ECS had a single health check that always replaces the task.

ALB with target-type: ip

Fargate pods have no node IP to register, so the Ingress annotation makes the ALB target pod IPs directly.

IRSA for the load balancer controller

The controller assumes an IAM role through the cluster's OIDC provider (trust scoped to kube-system:aws-load-balancer-controller), so no static credentials sit in a Kubernetes secret.

Immutable ECR tags, one tag per commit

Every image is addressable by the commit that produced it, so rollback means reverting one commit in the GitOps repo.

HPA between 2 and 5 replicas at 70% CPU

Declared in hpa.yaml with CPU requests and limits set on the container.

# deployment.yaml (excerpt)
livenessProbe:  { httpGet: { path: /live,  port: 5000 }, periodSeconds: 10 }
readinessProbe: { httpGet: { path: /ready, port: 5000 }, periodSeconds: 10 }

Issues I hit and fixed

  • CoreDNS stuck in Pending

    Cause: Fargate profiles covered production and argocd only, so nothing could schedule pods in kube-system; ArgoCD could not resolve its repo server.

    Fix: a third Fargate profile for kube-system (see eks.tf).

  • Load balancer controller rejected my subnets

    Cause: subnets were tagged for a cluster name that did not match the real cluster name.

    Fix: corrected the variable default to project-7-eks-cluster and re-applied so the kubernetes.io/cluster/… tags matched.

  • ALB created, then reconciliation failed with AccessDenied

    Cause: the published IAM policy lacked elasticloadbalancing:DescribeListenerAttributes, required by a newer controller version.

    Fix: added the action to lbc-policy.json.

  • Docker build failing on a non-existent package version

    Cause: requirements.txt pinned a Flask version that does not exist.

    Fix: pinned flask==3.1.3. The history below shows the failed runs before it went green.

Limitations and what I would do next

Be clear about scope. This is a self-directed lab, not a production system, and no live endpoint is published.

  • CI is build-and-push only. The repo has a pytest suite (4 tests) and a Flask app, but the workflow does not yet run lint, tests or an image scan. Wiring them in, with Trivy pinned to an immutable version, is the next step.
  • A personal access token (GITOPS_TOKEN) lets the pipeline push to the GitOps repo. No static AWS keys are used, but I would replace the token with a GitHub App or a narrowly scoped deploy key.
  • HTTP only. No TLS certificate or custom domain on the ALB.
  • Single environment. One production namespace; no staging or promotion flow.
